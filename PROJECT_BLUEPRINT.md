# CV Builder by PS - Project Blueprint Notes

These are personal interview notes for explaining the project clearly. This is not marketing copy. It is a technical map of what the app does, how the pieces connect, and the choices behind it.

## 1. Project Summary

CV Builder by PS is a full-stack web app that lets a user upload a PDF CV and receive ATS-style feedback generated by OpenAI.

The core workflow is:

1. User uploads a PDF CV in the React frontend.
2. Frontend sends the PDF to the backend API as `FormData`.
3. Express receives the file using `multer`.
4. Backend extracts text from the PDF using `pdf-parse`.
5. Backend cleans and limits the extracted text.
6. Backend sends the cleaned CV text to OpenAI.
7. OpenAI returns structured JSON feedback.
8. Backend sends the feedback to React.
9. React displays ATS score, strengths, weaknesses, missing keywords and suggestions.
10. React stores the last 5 reviews in browser `localStorage` so the user can track progress without an account.

The app also includes a CV templates page for common industries such as IT, data, finance, marketing, healthcare, education and retail.

Recent improvements added:

- local job description matching without extra OpenAI calls
- downloadable text review reports
- downloadable template-based CV PDFs
- richer local progress history with delete and trend stats
- CV version comparison between two saved reviews
- demo CV review that does not call OpenAI
- API rate limiting to protect OpenAI usage
- backend helper tests with Node's built-in test runner
- React split into components, data and utility modules

## 3. Main Files

`src/main.jsx`

This is the main React app. It now acts mostly as the orchestrator. It controls:

- View switching between the analyser page and templates page
- Calling `/api/analyse`
- Saving review history in `localStorage`
- passing state into components
- local job matching from the job description field

`src/components/`

Main frontend components:

- `UploadPanel.jsx`: PDF upload, drag-and-drop and privacy note
- `Results.jsx`: score cards, AI feedback, local match display and report download
- `HistoryPanel.jsx`: last 5 reviews, trend stats and delete/clear actions
- `TemplatesPage.jsx`: industry CV templates, template preview and browser-based CV builder
- `ScoreCard.jsx`: reusable score display
- `InsightList.jsx`: reusable feedback list

`src/data/cvTemplates.js`

Stores the static CV template data. This is frontend-only and does not use OpenAI.

`src/utils/`

Utility files:

- `history.js`: load/migrate local review history and format dates
- `jobMatch.js`: local keyword matching against pasted job descriptions
- `exportReport.js`: creates a downloadable text report in the browser
- `demoReview.js`: contains the free demo CV analysis result

`src/styles.css`

This contains:

- Tailwind imports
- Global font setup
- Custom animation keyframes
- The fancy `PS` brand styling

`server/app.js`

This is the main backend application. It controls:

- API routes
- PDF upload handling
- PDF text extraction
- CV text cleaning and length limiting
- OpenAI request
- JSON parsing and validation
- Temporary cache for repeated uploads
- Basic IP-based rate limiting
- Error handling

`server/index.js`

This starts the Express server locally on the port from `.env`.

`api/analyse.js` and `api/health.js`

These are Vercel API wrappers. They let Vercel use the same Express app when deployed.

`package.json`

Defines dependencies and scripts:

- `npm run dev` starts frontend and backend together
- `npm run client` starts Vite
- `npm run server` starts Express
- `npm run build` builds the production frontend
- `npm run check` checks backend JavaScript syntax
- `npm test` runs backend helper tests

`.env.example`

Shows the environment variables needed without exposing real secrets.

`.gitignore`

Prevents sensitive and generated files from being pushed:

- `.env`
- `node_modules/`
- `dist/`

`test/app.test.js`

Backend helper tests using Node's built-in `node:test` module. These cover text cleaning, text capping, JSON parsing and normalization helpers.

## 4. Frontend Flow

The frontend starts in `src/main.jsx`.

Important state:

- `activeView`: switches between analyser and templates
- `file`: stores the selected PDF
- `analysis`: stores AI feedback
- `meta`: stores returned file name, word count and extracted text preview
- `error`: stores user-facing error messages
- `isLoading`: controls the loading state during analysis
- `history`: stores the last 5 saved reviews

When a user uploads a file:

1. `selectFile()` checks the file exists.
2. It checks the MIME type is `application/pdf`.
3. It stores the file in React state.
4. It clears previous results and errors.

When the user clicks Analyse:

1. `analyseCv()` creates a `FormData` object.
2. It appends the file as `cv`.
3. It sends a `POST` request to `/api/analyse`.
4. It waits for JSON from the backend.
5. If the request fails, the error message is shown.
6. If it succeeds, the app displays the result and saves a small review summary to history.

The "Try demo CV" button loads a prewritten sample review from the frontend. It does not upload a file and does not call OpenAI.

The frontend never calls OpenAI directly. It only calls the backend route.

The job description field is used for local keyword matching after analysis. This does not increase OpenAI usage because the job description is not sent to OpenAI in the optimized version.

## 5. Backend Flow

The backend route is:

`POST /api/analyse`

Request format:

- `multipart/form-data`
- file field name: `cv`

Backend steps:

1. `multer` receives the uploaded PDF in memory.
2. The route checks that a file was uploaded.
3. `pdf-parse` extracts text from the PDF buffer.
4. `prepareCvText()` cleans and limits the text.
5. The backend checks that extracted text is not empty.
6. The backend checks `OPENAI_API_KEY` exists.
7. The route checks a basic per-IP rate limit.
8. The cleaned CV text is hashed with SHA-256.
9. The cache is checked.
10. If cached, the backend returns the saved analysis.
11. If not cached, OpenAI is called.
12. The OpenAI response is parsed, validated and normalized.
13. The result is returned to the frontend.

Response shape:

```json
{
  "fileName": "example.pdf",
  "wordCount": 650,
  "extractedTextPreview": "First 700 characters...",
  "cached": false,
  "analysis": {
    "atsScore": 78,
    "strengths": [],
    "weaknesses": [],
    "missingKeywords": [],
    "suggestions": []
  }
}
```

## 6. OpenAI Integration

The OpenAI API key is read only on the backend:

```js
new OpenAI({ apiKey: process.env.OPENAI_API_KEY })
```

The frontend never receives the key and never imports the OpenAI SDK.

Current default model:

```env
OPENAI_MODEL=gpt-4o-mini
```

The request uses:

- `chat.completions.create`
- `response_format: { type: "json_object" }`
- `max_tokens: 650`

The model is asked to return JSON only:

```json
{
  "atsScore": number,
  "strengths": string[],
  "weaknesses": string[],
  "missingKeywords": string[],
  "suggestions": string[]
}
```

## 7. Cost-Saving Choices

The app has several cost controls:

1. Cheap model

The default model is `gpt-4o-mini`, which is suitable for short structured CV feedback.

2. Text cleaning

The backend removes:

- null characters
- repeated spaces/tabs
- repeated blank lines
- leading/trailing whitespace

3. Text cap

The backend caps the CV text at `10,000` characters:

```js
const CV_TEXT_LIMIT = 10000;
```

This prevents very long PDFs from creating expensive prompts.

4. Short prompt

The prompt is intentionally brief and specific. It does not include long instructions or examples.

5. Output limit

The OpenAI response is capped:

```js
max_tokens: 650
```

6. Temporary cache

The backend hashes the cleaned CV text and stores the result for 30 minutes.

If the same cleaned CV is uploaded again, the backend returns the cached result instead of calling OpenAI again.

7. Local job matching

The job description matching is calculated in the browser using keyword overlap. It is deliberately not included in the OpenAI prompt, so it does not increase OpenAI token usage.

Cache details:

- `analysisCache` is an in-memory `Map`
- cache key is SHA-256 of cleaned CV text
- cache TTL is 30 minutes

Limitation: in-memory cache resets when the server restarts or when a serverless function cold-starts.

## 8. Error Handling

The backend handles:

- No PDF uploaded
- Non-PDF file type
- Invalid/unreadable PDF
- Empty extracted text
- Missing OpenAI API key
- OpenAI rate limit
- Local route rate limit
- Unexpected server errors

The frontend catches failed API responses and shows the error in the UI.

Examples:

- "Upload a PDF CV to analyse."
- "No readable CV text was found."
- "OPENAI_API_KEY is missing."
- "OpenAI rate limit reached."
- "Too many analyses from this browser."

For scanned PDFs, the backend now gives a clearer explanation that image-based PDFs may need OCR or a proper text-based export from Word/Google Docs.

## 8a. Local Job Matching

The app includes local job description matching.

How it works:

1. User pastes a job description in the frontend.
2. After CV analysis, the frontend compares the extracted CV preview and AI missing keywords against the job description.
3. `src/utils/jobMatch.js` extracts common keywords from the job description.
4. It calculates:
   - `matchScore`
   - `matchedKeywords`
   - `missingKeywords`

This feature does not call OpenAI and therefore does not increase API cost.

Tradeoff:

- It is cheaper and instant.
- It is less semantically smart than AI matching.
- It is still useful for ATS-style keyword coverage.

## 9. Review History

The app avoids accounts by storing progress in browser `localStorage`.

Storage key:

```js
resumeiq.reviewHistory.v1
```

The app stores only a compact review summary:

- file name
- date
- word count
- ATS score
- missing keyword count
- one summary suggestion

It does not store the full extracted CV text.

Added progress features:

- delete individual saved reviews
- clear all history
- show best score
- show overall trend from oldest to newest saved review
- show how many of the 5 slots are used
- select two saved reviews and compare ATS score and keyword-gap changes

Why this is useful:

- user can refresh the page and keep progress
- no database needed
- no login required
- simpler MVP

Tradeoff:

- history is only available on the same browser/device
- clearing browser storage removes history

## 11. Deployment Flow

Local development:

```bash
npm run dev
```

This starts:

- Vite frontend on `http://localhost:5173`
- Express backend on `http://localhost:5000`

Vite proxies `/api` requests to Express locally.

Production deployment:

1. Code is pushed to GitHub.
2. Vercel detects the push.
3. Vercel runs the build.
4. Frontend is deployed from `dist`.
5. API routes are handled through the `api/` wrappers.

Environment variables must be added in Vercel:

```env
OPENAI_API_KEY=real_key_here
OPENAI_MODEL=gpt-4o-mini
```

Do not add `PORT` on Vercel.

## 11a. PDF Export

The app can download a PDF report after analysis.

This happens entirely in the browser:

1. `Results.jsx` calls `downloadReviewReport()`.
2. `exportReport.js` creates a styled PDF with `jsPDF`.
3. The browser downloads the PDF.

No backend call is made, and no OpenAI credits are used.

## 12. Security Notes

The main security decision is keeping the API key on the backend.

Good practices already included:

- `.env` is ignored by Git
- frontend does not import OpenAI
- frontend only calls `/api/analyse`
- file uploads are limited to PDFs
- uploaded files are stored in memory rather than saved to disk
- file size limit is 6 MB
- API route has a basic rate limit
- OpenAI JSON is validated before being used

Things that could be improved later:

- move rate limiting to Redis or a hosted store for production reliability
- add CAPTCHA or abuse protection
- scan uploaded files more deeply
- add persistent database storage if accounts are introduced
- add stricter schema validation with a library like Zod

## 13. Important Tradeoffs

No accounts:

- simpler and privacy-friendly
- no database needed
- history only works per browser

PDF only:

- fits the MVP
- real CVs are often PDFs
- scanned PDFs may fail because `pdf-parse` needs embedded text
- OCR was not added because a reliable production OCR pipeline would add complexity and may require another service. The app instead handles empty scanned PDFs clearly and explains the issue to the user.

AI feedback:

- flexible and useful
- may vary slightly between runs
- should be treated as guidance, not a guaranteed recruiter score

In-memory cache:

- easy and fast
- saves duplicate API calls locally
- not persistent across deployments or server restarts

Static templates:

- free and fast
- easy to maintain
- less personalized than AI-generated templates

## 14. Interview Talking Points

Good short explanation:

"This is a full-stack CV analyser. The user uploads a PDF, the backend extracts text using pdf-parse, cleans and caps it to control cost, sends it to OpenAI using a cheap model, then returns structured JSON feedback. The frontend displays the ATS score and suggestions, calculates job matching locally, and stores the last five reviews locally so users can track progress without needing an account."

If asked why React:

"React made sense because the app has several interactive states: upload state, loading state, error state, results state, template selection and review history."

If asked why Express:

"I needed a backend because the OpenAI API key must not be exposed in the browser. Express gives a simple API layer for file upload, PDF parsing, validation and the OpenAI call."

If asked why localStorage:

"The goal was to avoid accounts for the MVP. localStorage is enough for lightweight progress tracking on the same device, and I only store review summaries rather than full CV text."

If asked about cost:

"I reduced cost by using `gpt-4o-mini`, cleaning and capping the CV text, keeping the prompt short, limiting output tokens, caching repeated uploads and doing job description matching locally instead of sending it to OpenAI."

If asked about limitations:

"The main limitation is scanned PDFs. If a PDF is just an image, `pdf-parse` may not extract useful text. The next step would be OCR using a dedicated OCR tool or service. Also, the cache and rate limit are in memory, so a production system might use Redis or a database."

If asked about privacy:

"The app does not store uploaded files on the server. The file is handled in memory, text is extracted, and only a small review summary is stored in the user's browser."

If asked about demo mode:

"The demo CV is a static sample analysis stored in the frontend. It lets people try the interface without uploading a real CV and without triggering an OpenAI request."

If asked what you would improve:

- Add OCR for scanned CVs
- Improve local job description matching with weighted phrases
- Add schema validation with Zod
- Move API rate limiting to persistent storage
- Add database-backed accounts if persistent history is needed
- Add more tests around file upload and API errors
